# Security Policy

`gvx` executes untrusted Linux programs and parses untrusted container images and volume files within a single host process. This document states the security boundaries enforced by the runtime, the versions that receive fixes, and the procedure for private vulnerability disclosure.

---

## 1. Security Boundaries

A security vulnerability is any defect that enables a guest program, an OCI image, a volume file, or a control peer to cross one of the boundaries listed below. See [`docs/components/hostlockdown.md`](docs/components/hostlockdown.md) and [`docs/architecture.md`](docs/architecture.md#39-host-self-lockdown-and-security-model) for the underlying containment design.

| Boundary | Enforced Invariant |
| :--- | :--- |
| **Guest to host** | Under `whpx`, `hvf`, and Linux `systrap`, guest instructions cannot invoke host system calls, access host memory, or create host processes. Untrusted workloads on Windows require `whpx`. |
| **Host lockdown** | After `hostlockdown.Apply()` succeeds, the host process cannot spawn child processes, open unbound host paths, or bind unauthorized sockets. |
| **Workspace and bind mounts** | `hostfs` opens no host file outside the explicitly mounted directory or single regular file. |
| **Untrusted input** | Malformed OCI layers, EROFS images, `ext4lite` volume files, checkpoint bundles, or registry responses return errors without memory corruption or host writes outside the cache. |
| **Network isolation** | `-net=wg` forwards guest packets exclusively through the WireGuard tunnel. `-net=none` provides no host network access. |
| **Control shim** | `containerd-shim-gvx-v2` never signals a PID read from metadata and never removes files owned by containerd. |
| **Release archives** | Every release archive carries a SLSA v1 build provenance attestation generated by `.github/workflows/release.yml` for the release tag. Reject any archive that fails provenance verification. |

### Verifying Release Provenance

Before executing a downloaded release archive, verify its Sigstore provenance bundle with the GitHub CLI (`gh`).

1. Download the archive and the release `.sigstore.json` bundle from GitHub Releases.
2. Run `gh attestation verify` against the exact repository, workflow, and tag reference.

```sh
VERSION=v0.22.10002026111600
ARCHIVE="rungvx-${VERSION}-darwin-arm64.tar.gz"
gh attestation verify "${ARCHIVE}" \
  --bundle "rungvx-${VERSION}.sigstore.json" \
  --repo gfire-sigs/gvx \
  --signer-workflow gfire-sigs/gvx/.github/workflows/release.yml \
  --source-ref "refs/tags/${VERSION}" \
  --deny-self-hosted-runners
```

### Documented Operational Limits (Not Vulnerabilities)

The following behaviors are deliberate design limits rather than security defects:

- On Windows, `--backend=auto` fails closed when `whpx` is unavailable unless `-allow-unconfined-systrap` or `Config.AllowUnconfinedSystrap` explicitly opts into `systrap`.
- On Windows, `systrap` relies on user-mode binary rewriting, a Low-integrity restricted token, and a Job Object; it provides no hardware or kernel system-call trap.
- On Android, mounting a host directory leaves `Status.UnboundFileOpenBlocked` false because Zygote's `untrusted_app` seccomp policy traps Landlock system calls.
- Passing `-lockdown=false` disables host self-lockdown for debugging.
- Under `-net=nat`, `-p`, and `--auto-publish`, a guest can communicate over the host network endpoints and loopback listeners explicitly exposed to it.

## 2. Supported Versions

`gvx` is under active pre-release development. Security fixes land on the `main` branch and ship in the subsequent release only.

| Version | Supported |
| :--- | :--- |
| `main` branch | Yes |
| Latest tagged release | Yes |
| Earlier releases | No |

---

## 3. Reporting a Vulnerability

Report suspected vulnerabilities privately through GitHub Security Advisories.

> [!WARNING]
> Do not disclose a vulnerability in a public issue, pull request, or discussion. Public disclosure exposes users before a remediation exists.

1. Open <https://github.com/gfire-sigs/gvx/security/advisories/new>.
2. Include the complete output of `rungvx version`.
3. State the host operating system, CPU architecture, and execution backend (`hvf`, `whpx`, or `systrap`).
4. Attach the minimal guest binary, OCI image reference, or volume file that reproduces the defect.
5. Identify which boundary from Section 1 the defect violates.

Maintainers respond within the private advisory thread and coordinate publication alongside the fix. Report defects that reproduce in unmodified upstream gVisor through the [gVisor security policy](https://github.com/google/gvisor/security/policy).
